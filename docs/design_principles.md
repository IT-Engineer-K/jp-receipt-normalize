# 設計思想: なぜ曖昧なら直さないか

## 1. 背景と課題

日本語の帳票（領収書、レシート、請求書など）をOCR処理すると、さまざまな表記揺れや文字化けが発生します：

- 全角数字と半角数字の混在
- 全角スペース、ノーブレークスペース、ゼロ幅文字の混入
- カンマとピリオドの誤読（例: `1,840` が `1.840` や `1 840` になる）
- 通貨記号の揺れ（`¥`、`￥`、`円`、`\`）
- 中国語OCRエンジンやマルチリンガルモデルに起因する簡体字・異体字（`计`、`圆`、`总`、`额` など）

従来のOCR後処理スクリプトやパイプラインでは、「それらしく見える値に自動置換する」ヒューリスティクスが使われることがあります。
しかし、会計・財務・税務・受発注などの業務帳票処理では、推測による誤補正は読み取りエラーと違って見た目上は正しい値になるため検出されにくく、誤った値がそのまま後続の処理に渡る危険があります。

## 2. コア原則

### 原則1: 監査可能性の保持
元のOCR出力文字列、文字位置、適用された変換ルール、変換前後の差分を破棄せずに保持します。
正規化結果は `Edit` オブジェクトの系列として追跡でき、なぜその結果になったのかを後から確認できます。

```python
@dataclass(frozen=True)
class Edit:
    rule: str
    source: str
    replacement: str
    start: int
    end: int
```

### 原則2: 「曖昧な補正」を黙って確定しない
人間が見れば文脈から「おそらく0だろう」と思える場合でも、文字レベルで曖昧性がある場合は自動確定せず、`status="ambiguous"` または警告理由（`reasons`）を付与して呼び出し元に返します。

#### 具体例:
- **英字「O」と数字「0」、英小文字「l」と数字「1」**:
  文脈なしに `O` を `0` に変換すると、型番や品名（例: `MODEL-O1`）を破壊します。`jp-receipt-normalize` の文字列正規化ではこれらを不可逆置換しません。
- **ピリオドによる桁区切り（例: `￥1.840`）**:
  日本円では通常3桁カンマ区切りですが、OCRがピリオドと誤認した可能性があります。しかし、外貨の小数表記や数量表記（`1.840kg`）の可能性も排除できません。そのため、`status="ambiguous"`, `reasons=("period_used_as_thousands_separator_candidate",)` として返し、最終決定権を業務ロジックまたは人間オペレーターに残します。
- **カタカナの長音記号（ー）とマイナス・ハイフン**:
  長音記号（`ー`、`ｰ`）は数字に挟まれている場合（`03ー1234ー5678`）のみハイフンに正規化します。それ以外の位置にある長音記号（`コーヒー`、`らーめん`、`ｺｰﾋｰ` → `コーヒー`）は長音記号として保持します。
- **空白区切り桁数・小数金額**:
  `1 840円` や `12 345円` のような空白区切りは `status="ambiguous"`, `reasons=("space_used_as_thousands_separator_candidate", ...)` として返し、部分一致（`1` と `840`）を確定候補にはしません。また、`0.50円` や `$12.50` のような小数金額は整数へ丸めず、`Decimal` のまま `status="ambiguous"` として保持します。
- **`元` と `円`**:
  `元` は `元年` や `地元` などの通常の語にも現れ、人民元を表す場合もあるため、`円` には変換しません。

### 原則3: 1件に決め打ちしない（複数候補の返却）
抽出API（`find_amounts`, `find_dates`, `find_phone_numbers` 等）は、テキスト内に見つかった候補をリストとして返します。
「レシートの中で最も大きい金額が合計金額だろう」といった業務固有の意味推論は非目標とし、ライブラリ内には含めません。

### 原則4: 判定ステータスの区分
抽出された候補は、以下のステータスに分類されます：

- `exact`: 原文のまま有効な値
- `normalized`: 非曖昧な変換（全角半角統一、カンマ除去など）を経て有効な値
- `ambiguous`: 複数の解釈が可能（2桁西暦、ピリオド桁区切りなど）
- `invalid`: チェックデジット不一致、実在しない日付など形式的に不正

### 原則5: 決定論的かつゼロ依存
- 入力とプロファイルが同一であれば、実行環境（OSや時刻）によらず同一の結果を返します。
- 外部API通信、LLM推論、OCRエンジンバイナリへの依存を持ちません。標準ライブラリ中心で動作します。
